## Technical Design

**Design views**: Metadata ownership and loader interfaces are relevant. State, temporal and data-flow designs are omitted because only existing Markdown discovery surfaces change.

### Trigger Descriptions

Use concise descriptions with these meanings; exact prose may be adjusted without broadening triggers:

| Skill | Trigger |
| --- | --- |
| `imm-brainstorm` | Use when the user explicitly requests Immune-Brain requirement clarification. |
| `imm-planner` | Use when the user explicitly requests Immune-Brain Spec and TaskIntent planning. |
| `imm-loop` | Use when the user explicitly requests execution or resumption of an Immune-Brain managed task. |
| `imm-pr-fix` | Use when the user explicitly requests Immune-Brain repair of GitHub PR feedback, conflicts or failing checks. |
| `imm-doc-prune` | Use when the user explicitly requests Immune-Brain removal of stale repository documentation. |
| `imm-agent-doc-maintain` | Use when the user explicitly requests Immune-Brain maintenance of agent instruction files. |

Descriptions answer when to use the Skill, not its internal workflow, output format, risk routing or tool sequence. A normal bug fix, one-function explanation, visual audit or question about instructions is not explicit entry into these workflows. Preserve existing mode names and invocation compatibility. Narrow descriptions and existing explicit-entry policy suffice; do not invent host-specific metadata flags or a new automatic classifier.

### Loader And Contract Ownership

Keep each loader's frontmatter, title, canonical relative link and only the minimal selection information needed to reach an existing branch such as `page_design`. Move duplicate detailed policy to the owned contract or reference already available there. A selected Skill must still expose its required approval/ownership constraints; shortening is not deletion of safety behavior.

Prefer adjusting tests to follow the canonical link over forcing the same interview algorithm into two files. The user-approved post-publication supplement requires branch-level lazy loading, not merely moving a full procedure into a different file: the entry loads common mandatory constraints and a compact route identifying the relevant sections; it reads long mode instructions, examples and recovery details only when their branch is selected or condition occurs. Keep each protected-operation constraint visible before that operation can run. Neither a loader nor the common canonical section may unconditionally require every reference or mode.

Implement this with explicit section routes in the existing owned canonical files and existing references; do not add a dispatcher or new reference files in this Slice. A whole-document load followed by ignoring most of it is not branch-level loading. New file extraction, if later proven necessary, requires a concrete scope and packaging delta before editing those paths; it is not implicitly approved here. No arbitrary line or character budget applies. Parse frontmatter and check route/target existence with existing repository test conventions; no new parser or dependency is necessary. These details refine A1/A2 without changing acceptance IDs, descriptors, dependencies or editable paths.

Synchronize descriptions across existing surfaces only where actually declared. Registry identity, role classes, mode lists, next actions and public entry count remain stable; regenerate mirrors/README if canonical metadata changes. Avoid incidental formatting or unrelated generated changes.

## Devil's Advocate Audit

- **Rollback resilience**: Revert loader/metadata/test diffs and regenerate declared copies; no data format migration or compatibility layer. Revert only this Slice's changes on shared canonical files.
- **Verification vanity**: A smaller file is insufficient. Assert that each explicit request still finds a valid canonical target, ordinary tasks are not promoted to Managed, and selected maintenance/native boundaries survive.
- **Spec dilution detection**: Do not drop a Skill, rename a mode, hide required decisions, retain duplicate exhaustive prose to satisfy old tests, or make all full contracts load through one universal entry.
