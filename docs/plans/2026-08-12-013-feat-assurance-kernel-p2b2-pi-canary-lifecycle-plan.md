## Goal

Publish the Pi-only mutation and authority route required to operate one already enrolled Kernel canary through terminal TaskRecord v2 closure without exposing generic mutation, dual write, or P2C default routing.

## Task

Implement the P2B2 executable slice after the dormant P2B1 exact-task enrollment route. This Plan builds and verifies lifecycle routing with isolated synthetic stores only; it does not perform the separately governed real enrollment operation.

## Output Language

Spec and Plan prose use English. Schema fields, CLI commands, file paths, JSON keys, enum values, Step IDs, and contract identifiers remain literal.

## Origin

P2B0 established exact-task enrollment, workspace backend pinning, and a v3 mutation guard. P2B1 established the sole Pi TUI enrollment route, which remains dormant because the governed live readiness evidence bundle is absent. R2C2 already provides a closed `TaskActionV2` reducer/application port, but it is intentionally unreachable from production and its mutation authority still has only a test issuer. An enrolled task therefore has no production route to record evidence, obtain independent QA/review authority, receive literal-user decisions, complete, or stop. The workspace-wide terminal claim also has no atomic release path, so a nominally terminal canary would permanently block later workspace routing.

## Research

- `plugins/immune-brain/runtime/kernel/application_v2.ts` is the sole lock/reread/reduce/CAS mutation path and already enforces Intent token identity, trusted diff equality, exact replay, workspace ownership, and privileged capability consumption.
- `plugins/immune-brain/runtime/kernel/authority_port.ts` currently exposes a shipped `createMutationAuthorityCapabilityForTest`; P2B2 must replace it with registry/application pairing and move test issuance under `tests/fixtures/`.
- `completionDecisionV2` requires no approvals for `routine`, independent `review` for `material`, and distinct `qa`, `review`, and `user` approvals for `critical`.
- Parent P2 requires host-validated isolated-child receipts for QA/review and Pi `ctx.ui.confirm` for literal-user actions. Arbitrary child JSON and command invocation are not authority.
- Parent P2 also requires drain-only rollback: a user-confirmed `begin_drain` must make the active backend claim irreversibly `draining` without changing TaskRecord phase or workspace ownership, while preserving same-task completion/confirmed stop and rejecting enrollment/v3 mutation.
- Pi SDK 0.84.1 supports extension-owned `createAgentSession`, `SessionManager.inMemory`, `SettingsManager.inMemory`, and explicit `DefaultResourceLoader`. `SessionManager.inMemory` alone does not isolate resources, and `extensionsOverride` runs after extension modules load. The executable child factory must use a fresh `0700` empty no-symlink child `agentDir` outside the repository, empty settings with `projectTrusted:false`, every `no*` flag, zero additional/factory paths, no project-trust preload, and fixed prompts so the pre-load path set is empty; overrides and post-start assertions are defense/evidence only. `tools: []` also filters custom tools, so the session passes exact custom tool names in `tools` and asserts the resulting registry is an exact closed set.
- Pi extension commands run before LLM input processing and can require `ctx.mode === "tui"`; tools remain LLM-callable and therefore may expose only ordinary non-privileged operations.
- The current global backend claim accepts `terminal`, while `assertNoKernelBackendForV3` rejects every present claim. Because no real P2B canary exists, P2B2 can refine the pre-live layout to active/draining workspace claim plus task-scoped terminal tombstone without migrating production state.
- The parent Roadmap explicitly assigns Kernel application service, Skill routing, and drain-only rollback to P2B. P2C host defaults and promotion remain separate.
- Architecture mapping found that a fully operable canary ultimately requires lifecycle application, QA/review authority, user authority, routing, and terminal release. A release-readiness probe recommended placing QA/review child authority in a P2B3 because it is a distinct trust/rollback boundary. The planner retains one P2B2 Plan but separates those boundaries sequentially: U1 closes host-neutral mutation/drain/terminal ownership without child authority; U2 alone adds the Pi child/user/routing trust boundary. U1 can close and remain dormant if U2 must replan, while no real enrollment occurs until both Steps close.

## Decisions

1. Keep reducer, completion predicate, storage CAS, and backend claim as the only workflow authorities; add no persisted scheduler or adapter-owned next-action state.
2. Expose a closed semantic canary application API rather than arbitrary `TaskActionV2` or caller-provided CAS/authority fields.
3. Replace mutation test-issuer singleton state with an explicit registry paired to the lifecycle application instance; create the sole production mutation pair inside the Pi lifecycle extension activation closure. Keep the P2B1 enrollment registry as a separate capability domain whose only handoff is the committed TaskRecord/workspace/claim tuple.
4. Permit one LLM-callable Pi tool only for status and ordinary executor operations. Privileged action kinds are structurally absent from its schema.
5. Mint QA/review capability only after the extension itself creates, observes, validates, and disposes a fresh in-memory child for one exact role and state snapshot. The child factory uses a fresh `0700` empty no-symlink agentDir outside the repository, empty untrusted in-memory settings, all five discovery suppressors, zero additional/factory paths, no trust preload, a fixed literal prompt, and a runtime-asserted custom-tool closed set. It explicitly reloads and passes the same loader/settings/agentDir to `createAgentSession`, and requires unique `tools` names to equal `customTools[].name` bidirectionally; post-load overrides are defense only and may not be treated as preventing module execution. Finally cleanup removes the child agentDir, and cleanup failure cannot create authority.
6. Treat TaskIntent as the parent-defined semantic authority. Parse the complete `acceptance[].verification` string only as strict canonical JSON for `assurance_kernel/verification_descriptor/v1` with exact fields `contract`, `runner_id`, `runner_version`, `argv`, `cwd`, `timeout_ms`, and `max_output_bytes`; P2B2 allows only runner ID `bun`. Never execute free text, an executable path, or a shell string. At extension activation, a host-owned resolver freezes the trusted Bun absolute realpath/device/inode/content hash/version; bind that identity, canonical descriptor, argv/cwd/environment identity and the committed TaskRecord `intent_snapshot`/`intent_ref` to receipt, capability, and mutation-lock revalidation.
7. Make `request_rework` Kernel-privileged: a QA/review capability binds the exact snapshot and full normalized findings digest, and the reducer/application reject direct untrusted invocation.
8. Mint user capability only after a fresh exact-action Pi TUI confirmation; command args, actor labels, booleans, and serialized descriptors remain untrusted. All assure/authorize continuations share a task-scoped linear invocation registry that rejects concurrency and late callbacks. Timeout/cancel wins `open -> cancelled`; a valid continuation must win `open -> committed` immediately before mint/apply, and failure remains closed with retry requiring a new invocation.
9. Treat `begin_drain` as a closed user-confirmed routing operation owned by the paired application/store lock, not as a TaskRecord phase or generic claim patch; permit only idempotent `active -> draining` and forbid reactivation.
10. Make one secure Kernel transaction module the sole writer of active/draining claims and terminal tombstones. Remove/package-hide direct claim write/remove APIs, reject workspace-global `terminal`, and bind all four authoritative path states in recovery markers.
11. Commit `done`/`stopped`, workspace release, active-claim removal, and a task-scoped terminal tombstone through that recoverable transaction.
12. Route active Kernel ownership through a dedicated `imm-canary-work` Skill while preserving v3 routing when no active claim exists.
13. Constrain the root package consumer surface with explicit exports and executable packed-consumer/host-registry tests; raw same-user filesystem imports remain outside the parent threat model.
14. Keep real enrollment, automatic orchestration, OpenCode/RPC privilege, P2C defaults, canary promotion criteria, and legacy retirement outside this Plan.

## Assumptions

- P2B1 remains dormant and no production TaskRecord v2 or backend claim has been created in this workspace.
- The installed Pi SDK's programmatic session APIs can be used from a trusted project extension without adding a second runtime package.
- The parent contract treats Git ownership as convention rather than authentication. Assurance uses the committed TaskRecord's normalized `intent_snapshot`/`intent_ref`, requires a secure sidecar reread to match, and accepts the complete verification string only as strict canonical JSON for `assurance_kernel/verification_descriptor/v1`. P2B2's runner registry contains only host-resolved `bun`; free-form strings, executable paths, shell syntax, PATH lookup during invocation, cwd escape, and environment overrides are ineligible. No existing Intent sidecars require migration because none are present, and P2B2 does not create one.
- Existing R2C2 reducer actions and completion rules are sufficient; discovery of a missing factual action or required lifecycle phase is a design change and routes to replan.
- A task-scoped terminal tombstone plus terminal TaskRecord is sufficient to preserve immutable backend affinity without a global terminal workspace claim.

## Execution Scope

P2B2 only: Kernel canary lifecycle application, Pi executor/QA/review/user authority routes, terminal ownership release, and Pi Skill routing for one already enrolled task.

## Deferred Phases

## Current-Slice Warning

This is not the full P2 Roadmap implementation Plan. It does not enroll a real task, create live evidence, select a canary automatically, add another privileged host, change the default backend, synthesize v3 state, or approve P2C.

## Plan Boundary

One coherent P2B2 slice covers the only safe route from an enrolled `working` TaskRecord through ordinary facts, independent assurance, literal-user decisions, and terminal ownership release. All components share one exact task identity, application authority, recovery transaction, Pi trust boundary, package surface, rollback policy, and final review gate.

## Boundary Rationale

Shipping only ordinary mutation would strand material/critical tasks at approval. Shipping authority without terminal ownership transfer would strand the workspace after completion. Shipping runtime application without Skill/host routing would leave the code unreachable, while shipping default routing would cross into P2C. These outcomes therefore belong together; real enrollment and broader promotion remain separate operational and Roadmap boundaries.

## Scope Pressure

The slice spans Kernel authority/application/storage, Pi SDK child sessions, extension tools/commands, packaged Skill contracts, and contract tests. Retain two sequential Steps because host routing depends on a closed recoverable Kernel application invariant, while both Steps remain one production boundary and one rollback. No Step may expand into automatic orchestration, additional hosts, default routing, new lifecycle phases, or live state creation.

## Devil's Advocate Audit

- **Rollback resilience**: U1 commits no live state during implementation and can be removed while P2B1 remains dormant. After any future enrollment, rollback disables new executor/assurance routes but preserves read-only status plus drain/user-confirmed stop until the active claim terminalizes. Terminal TaskRecords/tombstones remain immutable; no rollback reconstructs v3. Every terminal rename boundary has deterministic recovery.
- **Verification vanity**: Focused tests must fail on raw-action exposure, caller-supplied identity, direct `request_rework`, child JSON forgery, inherited/malicious child resources, unexpected tools/prompts/diagnostics, free-text or shell verification, mutable runner/cwd/environment identity, writable child tools, role reuse, stale snapshot, concurrent/late invocation, non-TUI privilege, confirmation bypass, exported/direct claim writer, claim/task mismatch, drain reactivation, each drain/terminal transaction crash point, global terminal deadlock, package subpath/host-registry issuer leakage, Skill route drift, or any live-state write. Verification includes actual Pi SDK construction with malicious discovery fixtures, a real packed consumer and Pi loader, full repository regression, Plan validation, and diff hygiene rather than file-presence or source-text assertions alone.
- **Spec dilution detection**: The Plan covers every parent P2B lifecycle obligation still missing after enrollment: application service, Skill routing, executor facts, independent QA/review receipt, literal-user authority, drain/stop, terminal release, restart recovery, no dual write, and Pi-only routing. It explicitly defers only real enrollment and P2C promotion, which require separate literal-user or evidence decisions rather than implementation convenience.
