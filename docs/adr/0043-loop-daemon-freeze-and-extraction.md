# Freeze In-Repo Loop Daemon and Extract Loop as an Independent Orchestrator

**Status:** accepted. Supersedes [ADR 0039](0039-loop-daemon.md),
[ADR 0040](0040-loop-interaction-protocol.md), and
[ADR 0042](0042-loop-leader-role-catalog.md) inside this repository, and amends
[ADR 0005](0005-unattended-initiative-batch-run.md) and
[ADR 0041](0041-simplified-configuration.md) on the retirement schedule below.
The Context records the tree as it stood before Slice 1.

## Context

- **Subsystem inversion and coupling asymmetry (`HEAD 136081195e`):**
  `plugins/immune-brain/runtime/loop_daemon/` has grown to 18,958 lines of TypeScript (27% of the 70,477-line runtime, exceeding `plugins/immune-brain/runtime/kernel/` at 14,185 lines and `plugins/immune-brain/runtime/unattended/` at 10,608 lines), alongside more than 25,000 lines of Loop and decision-model tests. Reverse dependencies from the rest of Immune-Brain into `loop_daemon/` span only six files (`plugins/immune-brain/runtime/v4_runtime.ts:300`, `plugins/immune-brain/runtime/commands/kernel.ts:58`, `plugins/immune-brain/runtime/config/layered_config.ts:6`, `plugins/immune-brain/runtime/host-core/loop_interactions.ts:24-26`, `plugins/immune-brain/runtime/host-core/runtime.ts:98,115`, and `plugins/immune-brain/runtime/host-core/mcp_runtime.ts:47`), whereas `loop_daemon/` reaches inward across 22 imports into `runtime/kernel/` (`agent_handlers.ts:35-46`, `drive_dispatcher.ts:35-36`, `dispatch.ts:29`, `interaction/github_channel.ts:19`) and 33 imports into `runtime/unattended/` and `runtime/lane_sessions/`. `plugins/immune-brain/runtime/decision_model/` has no live runtime caller outside `loop_daemon/judgement.ts:24-26` ([ADR 0039](0039-loop-daemon.md) Decision 3).
- **Split-brain session and worktree execution:**
  `loop_daemon/agent_runner.ts:29-102` spawns headless Host CLI processes directly in daemon worktrees for `clarify`, `plan`, `repair`, `leader`, and `analyze`, whereas `execute` crosses into `plugins/immune-brain/runtime/lane_sessions/index.ts:14-32` and `BatchAgreement` (`plugins/immune-brain/runtime/session/provider_registry.ts:54-84`).
- **Domain mismatch and live operational friction:**
  1. Immune-Brain governs how one change inside a worktree is scoped, verified (`QA`, `Review`), and settled with `.imm/audit/` proof; Loop solves tracker observation, backlog triage, multi-worktree DAG scheduling, PR/CI repair, and human interaction routing. Binding both into one state machine forces every tracked Issue through `TaskIntent`, `Enrollment`, and `BatchAgreement` ceremony even in repositories that want lightweight Issue-to-PR execution.
  2. Layering the [ADR 0042](0042-loop-leader-role-catalog.md) read-only Leader (`leader_agent.ts:104-144`, `leader_dispatch.ts`) over the [ADR 0039](0039-loop-daemon.md) Tier-2 `decision_model` funnel (`judgement.ts:205-216`, `0.75` threshold) and the rigid 12-state `WORK_ITEM_TRANSITIONS` table (`work_items.ts:49-67`) creates dual-brain stalls: below-threshold classifications route all open Issues into `escalate`, while initial `--state all` polling (`observer.ts:203-214`, `events.ts:116-153`) emits `E1_NEW_ISSUE` on already-closed Issues and floods `refused_transitions`.
  3. Worktree-scoped `.imm/state/loop/daemon.lock` forces one daemon process per repository, fragmenting GitHub polling quotas, machine-wide concurrency limits, and pending human interactions. Meanwhile `cli.ts:513-519` (`daemonLogin` vs `loop.allowed_actors`) and `guards.ts:131-139` (`isVerifiedActor`) block single-account local setups unless routed through Immune-Brain's own Host MCP tools.

## Decision

1. **Freeze in-repo `loop_daemon/`.** Effective immediately, `plugins/immune-brain/runtime/loop_daemon/`, `plugins/immune-brain/bin/imm-loop`, `plugins/immune-brain/skills/imm-loop/`, and `plugins/immune-brain/runtime/decision_model/` are frozen in feature scope. Only fixes for blocking defects, security issues, or cross-module contract breakage are accepted until removal.
2. **Evolve Loop in an independent repository as a general-purpose orchestrator.** The successor system lives in its own repository with zero code, package, or SQLite dependency on Immune-Brain. It dispatches Claude Code, Pi, and Antigravity directly on ordinary repositories; Immune-Brain becomes an optional high-assurance execution backend rather than a prerequisite.
3. **End-state boundary: multi-worktree orchestration in Loop, single-worktree Assurance in Immune-Brain.**
   - **Loop** owns tracker polling, deterministic fast-paths, Leader scheduling, worktree lifecycle, multi-task DAG execution and branch integration, session supervision, human interaction channels, and PR creation/repair (supporting both standing daemon operation and local batch runs).
   - **Immune-Brain** converges on a single-worktree, single-task **Assurance Kernel** (`Spec`, `TaskIntent`, `Enrollment`, `Scope Envelope`, deterministic `QA`, independent `Review`, and `.imm/audit/` `Settlement`). Existing interactive `/drive` batch support (`runtime/unattended/` and `runtime/lane_sessions/`) stays operational during the transition and retires only after the standalone Loop covers local multi-task execution.
4. **Zero-dependency narrow CLI + JSON integration seam (`imm-kernel --json`).** Loop defines a pluggable workspace driver/verifier contract whose default implementation validates Git commits plus repository-declared shell verification commands. When a repository opts into the Immune-Brain backend, Loop interacts with Immune-Brain exclusively via versioned, non-interactive `imm-kernel --json` subprocess calls — extending the CLI boundary already used in `plan_drafter.ts:61` and `leader_dispatch.ts:126` to cover controlled headless Enrollment (`policy_auto` or verified approval proof), Assurance/blocker inspection (`imm-kernel inspect --json`), mid-run literal-user decision relay, and settled `.imm/audit/<task-id>/` verification. Neither system imports the other's TypeScript modules or reads the other's `.sqlite` / internal state files.
5. **Deterministic fast-path + single-brain Leader + code guards.** The standalone Loop drops the mandatory Tier-2 `decision_model` probability gate and the rigid 12-state `WorkItem` transition table (`decision_model` prefiltering, if ever used, becomes an optional external plugin). Unambiguous mechanical signals (managed PR CI failure, merge conflict, explicit labels/commands) route directly through deterministic rules; ambiguous open Issues and backlog ordering are decided by one fingerprint-gated, read-only Leader session; concurrency caps, budgets, branch prefixes, and `no_touch` path boundaries remain 100% enforced by deterministic code guards.
6. **Standalone interaction surfaces and tiered identity posture.** Loop provides its own CLI/TUI inbox (`inbox`, `approve`, `steer`) plus optional standalone MCP/IM adapters, severing the three `host-core` reverse dependencies in Immune-Brain. Dispatched worker sessions run with GitHub write credentials stripped (all remote pushes and comments flow through the Loop process), supporting both a zero-bot `personal` local posture (local CLI confirmation + Draft PRs without startup deadlock) and an `isolated` team posture (dedicated GitHub App / Bot identity for remote `/approve` workflows, preserving Kernel anti-forgery rules when Immune-Brain is enabled).
7. **Single machine-level multi-repository daemon.** One `loopd` process manages multiple registered repositories (`watch <repo>`), sharing machine-wide session concurrency slots, GitHub API rate budgets, and one unified human inbox, while each repository carries only lightweight declarative policy configuration (alongside on-demand foreground single-repo runs).
8. **Orthogonal to Herdr, with `herdr-core` (`hc`) as primary session substrate.** Loop remains a separate system from [Herdr](0038-supervised-session-port.md), using `herdr-core` (`hc run --bg --no-parent`, OSC 7501 status reporting, live Herdr UI visibility and attach/takeover) as its first-class backend for long-running sessions (`execute`, `repair`, `plan`) and falling back to headless Host CLI subprocesses for short read-only calls (`leader`) or environments without `hc`.
9. **Adaptive default workflow and three-phase cutover.**
   - On repositories without Immune-Brain, Loop runs an adaptive pipeline: clear single-point Issues go straight through `execute -> shell verify -> PR`, while complex or ambiguous Issues run `clarify` / lightweight DAG `plan` (with optional approval) before parallel worktree execution.
   - **Cutover sequence in this repository.** Retirement runs first, so interactive `drive` can build the later Slices on itself:
     - **Slice 1 (`retire-loop-daemon`):** delete `runtime/loop_daemon/`, `bin/imm-loop`, `skills/imm-loop/`, `runtime/decision_model/`, the offline evals that consume it, the `loop` and `decision_models` configuration keys, the `tracker_approval` and `policy_auto` confirmation sources, and `loop_interactions` / `answer_loop_interaction` / `steer_loop_work_item` from every Host; supersede ADRs `0039`, `0040`, and `0042`.
     - **Slice 2:** implement the `takt/gate/v1` CLI bridge (`GateRequest` on stdin, `GateResponse` on stdout) that consumes a signed Ed25519 `ApprovalProof`, relays blocking decisions, and returns the `.imm/audit/<task-id>/` proof reference. It is the headless Enrollment seam Decision 4 describes; `policy_auto` does not return.
     - **Slice 3:** decouple interactive single-task `/drive` from the batch orchestration into a pure single-task Kernel path, retire `runtime/unattended/`, and amend [ADR 0005](0005-unattended-initiative-batch-run.md).

## Consequences

- From Slice 1, `imm-loop` and the three Loop tools no longer exist, and a configuration file that still carries `loop` or `decision_models` is reported as `config_invalid` and blocks a batch until `imm-kernel config migrate --write` removes the key.
- Slice 1 removes ~19k lines of `loop_daemon/` + ~1k lines of `decision_model/` + their coupled tests, leaving Host plugins leaner for interactive users.
- Kernel authority invariants stand: when Immune-Brain is enabled as a Loop backend, `TaskIntent`, `Enrollment`, `Scope Envelope`, `QA`, `Review`, and `.imm/audit/` `Settlement` remain governed solely by `runtime/kernel/`.

## Rejected

- **In-place refactoring or monorepo `packages/` incubation inside `immune-brain`.** Rejected because ~44k lines of implementation and tests encode per-repo `.imm/state/loop/`, the 12-state transition table, Tier-2 `clef` thresholds, and `BatchAgreement`; evolving a multi-repo daemon inside Immune-Brain's Managed risk-floor gates adds friction without sharing runtime state.
- **Wholesale copy of `runtime/loop_daemon/` into the new repository.** Rejected because `agent_handlers.ts` and `drive_dispatcher.ts` carry 55+ internal imports into `kernel/`, `unattended/`, and `lane_sessions/` plus the dual-brain architecture being retired.
- **Prompt-only black-box or npm SDK integration with Immune-Brain.** Prompt-only invocation cannot satisfy headless `Enrollment` gates or relay structured `unresolved_user_decision` findings; importing `@immune-brain/kernel` as an npm library couples TypeScript and `.imm/state/kernel.sqlite` schema versions across independent release cycles.
- **Merging Loop into Herdr.** Rejected to keep terminal/PTY multiplexing (`herdr` / `hc`) orthogonal to tracker, DAG, and PR orchestration.
