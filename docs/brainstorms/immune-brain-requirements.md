# Immune-Brain Workflow Rewrite Requirements

## Summary

Immune-Brain 的第一版不重建整套系统，而是借用 `compound-engineering` 的主链路 `brainstorm -> plan -> work -> review -> compound`，只重写中间的 `plan + work + review`。重点是把一次迭代压缩成可独立验证的小结果，减少 `review -> work` 多轮往返后仍需要人工收口的情况。

---

## Problem Frame

当前工作流的主要问题不是没有主流程，而是主流程中段失真。`ce-plan` 在真实任务里容易把一次迭代规划得过大，导致后续 `work` 实际执行时吞入过多内容，单轮改动的目标不够清楚，也不容易独立验证。

这会把问题继续传递到 `review`。当一次迭代本身过大时，`review -> work` 即使跑了多轮，也仍会残留结构性问题，最后只能由人工重新拆任务、重新判断边界、重新收口。真正浪费时间的不只是某个 skill 的单点质量，而是这三个环节连续放大了“单轮任务过大”的问题。

第一版的目标不是兼容原始 `ce-*` 行为，也不是先解决所有 skill 冗余，而是先证明一个更适合个人高强度使用的工作方式是否成立：用更强的拆分纪律约束 `plan`，再用更收敛的 `work` 和 `review` 语义，把问题限制在当前小步内，而不是让人工接手残局。

---

## Actors

- A1. 用户 / 主操作者：提出任务、判断业务取舍、在必要时决定是否继续某个迭代。
- A2. Planning agent：按用户可验证结果组织目标小迭代。
- A3. Work agent：只消费当前迭代，完成该小步承诺的结果，不主动扩张范围。
- A4. Review agent：审查当前小步是否闭合，指出当前小步内的问题，并阻止未收敛的大步继续推进。

---

## Key Flows

- F1. 小步规划流
  - **Trigger:** 用户给出一个原本会触发较大计划的真实任务。
  - **Actors:** A1, A2
  - **Steps:** 规划环节先定义最终目标，再按可独立闭合结果组织小迭代；每个迭代只承诺一个清晰结果；任何无法单独验证的任务必须继续拆小，动作型小步必须合并回对应结果。
  - **Outcome:** 计划结果不再是一组大块任务或动作清单，而是可以逐个消费的小步。
  - **Covered by:** R1, R2, R3

- F2. 单步执行流
  - **Trigger:** 某个小迭代被选为当前工作单元。
  - **Actors:** A1, A3
  - **Steps:** 执行环节只接收当前小步的范围与目标；实现过程中不得默认连带完成相邻小步；若执行发现当前小步仍过大，应中断并要求回到规划或重拆。
  - **Outcome:** 一次实现只围绕当前小步展开，避免把计划重新膨胀成大迭代。
  - **Covered by:** R4, R5, R6

- F3. 收口审查流
  - **Trigger:** 当前小步完成后进入审查。
  - **Actors:** A1, A3, A4
  - **Steps:** 审查环节先判断本轮是否闭合，再指出当前小步内的缺口；如果问题暴露的是拆分错误，而不是局部实现问题，则不继续局部修补，而是要求回退重拆。
  - **Outcome:** `review -> work` 的往返聚焦在当前小步内，减少演变成整轮人工接管的情况。
  - **Covered by:** R7, R8, R9

---

## Requirements

**主流程边界**
- R1. 第一版必须保留 `brainstorm -> plan -> work -> review -> compound` 这条主链路，作为整体工作方式的外部骨架。
- R2. 第一版只重写 `plan + work + review` 的语义与协作边界，不要求兼容原始 `ce-*` 的具体行为。
- R3. `brainstorm` 与 `compound` 在第一版中必须保持不变，不纳入首轮改造范围。

**规划拆分**
- R4. `plan` 必须按“用户可验证结果”拆分任务，而不是按宽泛主题、角色分工或大块实现阶段拆分。
- R5. 每个计划小步只允许承诺一个清晰结果；如果一个小步需要依赖多个混合目标才能证明价值，则必须继续拆分；如果多个小步只是同一结果的执行动作，则必须合并。
- R6. 任何无法独立验证完成与否的小步都不能作为可执行计划输出，必须在规划阶段继续细化。

**执行约束**
- R7. `work` 必须只消费当前计划小步，不能把相邻小步、顺手优化或额外重构默认并入当前执行范围。
- R8. 当 `work` 发现当前小步实际仍过大、目标不清或无法闭合时，必须显式中止当前推进，并返回重拆或重判边界，而不是继续硬做。
- R9. `work` 的成功标准必须是“完成当前小步承诺的可验证结果”，而不是“顺便多做一些相关事情”。

**审查收口**
- R10. `review` 必须先判断当前小步是否足够小、边界是否清楚、是否已经形成闭环，再进入具体问题检查。
- R11. 当 `review` 发现问题属于当前小步内部的缺口时，应推动当前小步内修复，而不是把范围扩大成下一轮大任务。
- R12. 当 `review` 发现问题本质上来自错误拆分或过大迭代时，必须明确要求回退重拆，而不是继续通过多轮 `review -> work` 消化结构性问题。

**有效性标准**
- R13. 第一版必须能支持至少一类原本容易被规划成大迭代的真实任务，被组织成可独立完成的小步，数量由可闭合结果自然决定。
- R14. 每个小步都必须可以单独进入 `work -> review`，并在不依赖其余小步同时落地的情况下被验证是否完成。
- R15. 第一版的评价重点不是让 `review` 零问题，而是把问题限制在当前小步内，降低因为拆分过粗而导致的人工接管需求。

---

## Acceptance Examples

- AE1. **Covers R4, R5, R6.** 给定一个原本会被规划成“大型功能开发”的任务，当进入 `plan` 时，输出结果应按可独立闭合结果组织小步，且每个小步只表达一个可以单独判断完成与否的结果。
- AE2. **Covers R7, R8, R9.** 给定当前只批准执行某个计划小步，当 `work` 过程中发现还牵涉额外目标或额外改造时，系统应停止扩张范围，并要求回到边界判断，而不是直接一起做完。
- AE3. **Covers R10, R11, R12.** 给定 `review` 发现的问题已经超出当前小步可修范围，当进入下一轮判断时，系统应把问题标记为拆分失败并要求重拆，而不是继续在同一轮链路上堆叠修补。
- AE4. **Covers R13, R14, R15.** 给定一个真实任务原本会导致多轮 `review -> work` 后仍残留问题，在新流程下，至少应能把遗留问题收敛为当前小步内的局部修正，或在更早阶段显式触发回退重拆。

---

## Success Criteria

- 对于原本容易被规划成大迭代的真实任务，新的 `plan` 能稳定产出可独立验证的小步，而不是一组大块任务或动作清单。
- `work` 在单轮执行中不再默认扩张范围，能围绕当前小步收敛。
- `review` 能区分“当前小步内的问题”和“拆分本身就错了”，并在后者出现时尽早阻断。
- 与现有使用体验相比，人工介入更多变成取舍和裁决，而不是反复替系统重新拆分任务和收残局。
- 后续实现或规划环节在阅读本需求文档后，不需要再自行发明第一版到底改什么、先不改什么、如何判断是否有效。

---

## Scope Boundaries

- 第一版不改 `brainstorm`。
- 第一版不改 `compound`。
- 第一版不追求兼容原始 `ce-*` 的具体行为细节。
- 第一版不要求一次性解决所有 skill 冗余问题。
- 第一版不要求建立完整的新命名体系或替换整套 CE 能力入口。
- 第一版不要求先解决长期记忆、自愈、跨项目移植等更大系统议题。

---

## Key Decisions

- 保留 CE 主链路，只重写中段：这样可以复用现有工作骨架，同时把改造集中在最直接影响效率的失真环节。
- 第一版优先个人使用体验，不优先兼容：目标是先做成“更适合你自己”的系统，而不是做成 CE 的温和增强版。
- 把 `plan` 作为主改造点：因为 `work` 和 `review` 的问题在当前判断下主要是由计划粒度过粗持续放大。
- 用“用户可验证结果”而不是“实现主题”或固定数量作为拆分单位：这样更容易压小迭代，并让 `work` 与 `review` 都围绕可判断的结果收敛。

---

## Dependencies / Assumptions

- 第一版仍以 `compound-engineering` 现有主流程为参考来源，而不是完全脱离其工作模型。
- 后续实现阶段需要定义“什么算可验证结果”与“何时判定必须回退重拆”的具体执行规则。
- 后续实现阶段需要决定是直接改写现有 skill，还是通过新的包装层重定义 `plan + work + review`。
- 第一版验证需要挑选至少一个你真实会做、且过去确实容易膨胀成大迭代的任务来试跑。
